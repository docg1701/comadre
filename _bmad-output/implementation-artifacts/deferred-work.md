- **``issue-key --rpm`` upper bound.** Story 1.6 caps ``update-key --rpm`` at 10 000 (closes Story 1.2 deferred). ``issue-key`` still accepts unbounded RPM. - **Cross-cutting ``_load_settings_and_tz`` / ``_resolve_key_target`` adoption.** Story 1.6 introduced these shared helpers for the three new commands; ``issue-key`` / ``list-keys`` / ``show`` / ``update-customer`` still inline their own settings→TZ→DB-open ladder. ## Deferred from: code review of story-1-5 (2026-04-17)

Subsumed by the Story 1.5 patch that maps `RuntimeError` to exit 5; revisit if multi-writer deployments ever land (project's single FIFO queue makes this extremely unlikely today). [`src/comadre/keys/db.py:333-340`]
- **Non-NUL control characters in `--add-note` (CR `\r`, ANSI escape `\x1b`, other C0 controls).** Only NUL is rejected today. CR corrupts later `grep`/tail output; ANSI escapes could forge terminal formatting when `render_customer_detail` later prints the note. Cross-cutting with Story 1.4's deferred Rich-markup-injection item — fix together in a single "printable-only operator text" hardening pass. [`src/comadre/keys/cli/commands/customers.py:678-692`]
- **Unbounded `--add-note` length and unbounded cumulative `customer.notes` growth.** Story 1.1 and Story 1.5 both defer this; the project-wide cap decision needs to happen once across `create-customer --notes`, `update-customer --add-note`, and any future note-touching surface. Pick a cap (e.g. 1 KiB per append, 64 KiB cumulative) when the next `--notes`-touching story lands. [`src/comadre/keys/cli/commands/customers.py:685-692`, `src/comadre/keys/db.py:297-303`]
- **Audit-details JSON assertions compare exact byte strings.** Tests assert literals like `'{"fields": ["email"]}'`. If `log_event` ever switches `json.dumps` separators or indentation, every one of these tests breaks even though semantics are unchanged. Migrate to `json.loads(row["details_json"]) == {"fields": [...]}` in the next test-hygiene pass. [`tests/test_keys_db.py:457,487,574,692,729`, `tests/test_keys_cli_update_customer.py:961,993,1077,1485,1507`]
- **`UpdateCustomerResult.customer` does a full post-commit `get_customer_detail` round-trip to read only `.id` (already known) and `.name`.** The extra SELECT is wasted work on the happy path. Optimization — replace with a targeted `SELECT name` inside the existing transaction, or reshape `UpdateCustomerResult` to carry only the fields the CLI actually uses. Not a bug; revisit on the next `update-*` surface (Story 1.6 `update-key` will double the footprint). [`src/comadre/keys/db.py:333-344`, `src/comadre/keys/cli/commands/customers.py:778-779`]
- **`_logger.info` raising after a successful commit would bypass `render_confirmation`.** Structured-logging handlers can throw (disk full, rotator race). After commit, the operator-visible confirmation is what matters; wrap the log call in `contextlib.suppress(Exception)` when next touching the log path so a handler fault can't hide a successful mutation. [`src/comadre/keys/cli/commands/customers.py:772-779`]
- **No concurrent-update regression test.** Two parallel `update-customer` invocations against the same row are not covered. Project's single FIFO queue makes realistic write contention bounded, but a regression test with two subprocesses would pin the current "SQLite LAST_WRITE_WINS" semantics so a future schema change doesn't silently drift. [`tests/test_keys_cli_update_customer.py`]

## Deferred from: code review of story-1-4 (2026-04-17)

- **`ShowTarget.value` typing forces `cast(...)` at every call site.** The discriminated-union `value: CustomerDetailRow | KeyDetailRow | list[KeyDetailRow] | None` requires every reader to `cast(...)` the variant out, even after narrowing on `result.kind`. Mypy can't bind the variants to the discriminator without `match`-with-variant-classes or a `TypeGuard` shim. Spec §Task 8.2 explicitly accepts this shape, but a future cleanup could split into per-kind dataclasses with a `Union[…]` alias. [`src/comadre/keys/db.py`, `src/comadre/keys/cli/commands/customers.py`]
- **`list_audit_events` IN-clause unbounded against `SQLITE_MAX_VARIABLE_NUMBER`.** `target_ids` is interpolated into a positional-`?` list with no chunking. Modern SQLite caps at 32k vars by default so the surface is theoretical today, but a customer that ever accumulates hundreds of keys + a bulk audit-tail query would silently approach the cap. Address with chunked OR-merging or a temp-table join when a high-volume operator emerges. [`src/comadre/keys/db.py`]
- **Rich markup injection via stored `name` / `notes` / `customer_name` in DetailPanel bodies.** Pre-existing pattern from Story 1.2/1.3 panels — stored data is interpolated into Panel content with `markup=True` (the rich default). A customer name like `[red]Acme[/]` would re-style the panel; a stray `[/]` could trigger `rich.errors.MarkupError`. Cross-cutting fix: wrap interpolated row-data with `rich.markup.escape(...)` across all `render_*` helpers. Story 1.4 doesn't add the regression — it just preserves it. [`src/comadre/keys/cli/output.py`]
